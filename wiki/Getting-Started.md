# Getting Started

Rung starts by defining **independent success**, not by immediately explaining the subject.

## 1. Name the skill

Write the target as something the learner will eventually *do*.

Weak:

> Understand scene structure.

Stronger:

> Diagnose whether a scene has a clear decision, consequence, and causal connection, then revise it without being told which element is missing.

The distinction matters because a vague goal cannot be tested reliably.

This adapts a MAPS_Lean planning rule: define an observable **DONE** state before execution rather than treating activity itself as success. See [MAPS Adaptations](MAPS-Adaptations) and the MAPS [`PROJECT_BOOTSTRAP.md`](https://github.com/BigCatMellow/MAPS_Lean/blob/main/playbook/PROJECT_BOOTSTRAP.md).

## 2. Define the final proof

Ask:

> What would convince us that the learner can now do this without the teacher?

A useful final proof might require the learner to:

- recognize when the skill applies;
- choose the method without being told which method to use;
- execute it;
- explain why it works;
- detect an important error;
- use it on a meaningfully changed example.

Do not define mastery as "finished the current project." A project can be completed through heavy assistance while the underlying skill remains dependent.

## 3. Run a cold baseline

Before significant instruction, give a small realistic problem and ask the learner to attempt it without hints.

The purpose is diagnosis, not grading.

Look for:

- knowledge already demonstrated;
- knowledge the learner reports but cannot yet demonstrate;
- missing prerequisites;
- recurring habits;
- misconceptions;
- poor method selection;
- failures to check one's own work.

When factual status matters, Rung borrows the MAPS evidence labels:

- **VERIFIED** — demonstrated or directly checked;
- **REPORTED** — stated but not demonstrated here;
- **ASSUMED** — provisionally treated as true;
- **UNKNOWN** — not enough evidence.

MAPS uses these labels to keep assumptions from silently becoming trusted facts. See [`AGI_STANDARD.md`](https://github.com/BigCatMellow/MAPS_Lean/blob/main/playbook/AGI_STANDARD.md).

## 4. Set the learning boundary

Write three short fields:

**Current target**  
What are we learning now?

**Useful but later**  
What related ideas should be captured but not pursued yet?

**Out of scope**  
What are we deliberately not trying to master in this learning arc?

This prevents an interesting tangent or project-polishing task from quietly replacing the actual skill target.

## 5. Build diagnostic questions

Identify the 2–6 recurring failure modes in the domain and create a question that exposes each one.

A diagnostic question should be reusable. It should eventually become a question the learner asks themselves.

Example from narrative work:

> **Who is choosing and who is being dragged?**

This is better than "What do you think is wrong with the scene?" because it tests a specific property—agency—and can be applied to many scenes.

For each question, record:

| Failure mode | Diagnostic question | What a good answer demonstrates |
| --- | --- | --- |
| [failure] | [question] | [evidence] |

## 6. Begin below the learner's failure point

Do not make every session start with a lecture.

Start with an attempt. If the learner can reason productively, question and cue. If the learner lacks the concept required to reason at all, explain the minimum prerequisite and return the work to them.

This is the central Rung rule:

> **Make the learner do as much of the important thinking as they can productively do; supply only the structure they currently cannot provide themselves.**

See [The Assistance Ladder](Assistance-Ladder).

## 7. End with evidence

Before ending a learning arc, change the problem.

The learner should not know the correct method merely because the current example looks exactly like the examples used during instruction.

Use [Mastery and Transfer](Mastery-and-Transfer) to decide whether the skill is actually independent.
